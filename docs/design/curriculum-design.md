# 커리큘럼 설계서

> Claude Code와 Codex로 **대규모 개발**을 수행하기 위한 실전 가이드의 전체 설계.
> 이 문서는 가이드의 "PRD"이며, 모든 모듈·프로젝트·숙제는 이 문서를 기준으로 작성합니다.

---

## 1. 목적과 범위

### 1.1 목적
- AI 코딩 에이전트(Claude Code, Codex)를 **장난감 수준이 아닌 수만~수십만 라인 규모**의 프로젝트에 적용하는 방법을 체계화합니다.
- 개념 설명보다 **따라하기(Follow-along) → 숙제(Homework) → 회고(Retro)** 의 반복으로 몸에 익히게 합니다.
- 결과물이 실제 저장소(문서 사이트, 서비스 코드, PR 이력)로 남게 하여 포트폴리오가 되게 합니다.
- 사람이 따라가는 실행 가이드와 Claude Code·Codex가 읽는 작업 지침을 함께 제공합니다. 요구사항 → 설계 → Task → 구현 → 검증 → 인수인계가 파일과 ID로 연결되어야 합니다.

### 1.2 대상
| 레벨 | 설명 | 권장 시작점 |
|---|---|---|
| L1 입문 | AI 코딩 도구를 채팅 정도로만 써본 개발자 | Module 00부터 |
| L2 실무 | 개인 프로젝트에 에이전트를 써봤지만 규모가 커지면 무너지는 경험이 있음 | Module 02부터 |
| L3 리드 | 팀 단위 도입, 거버넌스, 멀티 에이전트 운영을 고민하는 리드/아키텍트 | Module 05, 06 + Project C |

### 1.3 범위 밖
- 특정 언어/프레임워크 자체의 교육 (참조 스택은 제공하되 언어 교육은 하지 않음)
- 모델 학습/파인튜닝, LLM 애플리케이션 개발(RAG 등) — 이 가이드는 "AI로 개발하기"이지 "AI를 개발하기"가 아닙니다.

## 2. 설계 원칙

1. **Spec First** — 에이전트에게 코드를 시키기 전에 반드시 문서(PRD → 설계 → 작업 명세)를 만듭니다. 대규모 개발의 실패 원인 1순위는 모호한 지시입니다.
2. **Context is a Budget** — 컨텍스트 윈도우는 유한한 자원입니다. `CLAUDE.md`/`AGENTS.md`, 작업 분할, 서브에이전트, 세션 리셋으로 관리합니다.
3. **Verify, Don't Trust** — 모든 산출물은 테스트·린트·타입체크·리뷰로 검증됩니다. "에이전트가 됐다고 함"은 완료가 아닙니다.
4. **Small Batches, Many Agents** — 작은 단위의 작업을 병렬로(worktree, 클라우드 세션) 돌리고 PR로 통합합니다.
5. **Two Models, Cross-Check** — Claude와 Codex를 경쟁이 아닌 상호 검증 관계로 씁니다 (한쪽이 구현, 다른 쪽이 리뷰).
6. **Tool-Agnostic Core, Tool-Specific Recipes** — 원칙은 도구 독립적으로, 실행 방법은 Claude / Codex 각각의 레시피로 제공합니다.
7. **Dogfooding** — 이 가이드 저장소 자체가 Project A(문서화 프로젝트)의 레퍼런스 구현입니다.

### 3.1 모듈과 프로젝트의 관계

모듈은 **짧은 레슨(1~3시간)** 으로 개념과 기법을 익히고, 프로젝트는 **수 주짜리 마일스톤**으로 그 기법을 실전에 적용합니다.

| 모듈 | 핵심 주제 | Project A (문서) | Project B (개발) | Project C (레거시) |
|---|---|---|---|---|
| 00 Foundations | 에이전트 동작 원리, 도구 비교 | A0 | – | – |
| 01 Environment | CLAUDE.md/AGENTS.md, 설정, MCP, 권한 | A1 | B0 | – |
| 02 Spec-Driven | PRD, ADR, 설계서, 작업 분해 | A2 | B1 | – |
| 03 Workflow | Plan→Implement→Verify, TDD, Git | A3 | B2, B3 | C1 |
| 04 Quality | 테스트, 교차 리뷰, 보안 | A4 | B4 | C2 |
| 05 Scaling | 병렬 에이전트, 모노레포, CI 자동화 | – | B5, B6 | C3 |
| 06 Team & Ops | 비용, 지표, 거버넌스, 팀 규칙 | A5 | B7 | C4 |

### 3.2 실제 개발에 적용하는 실행 경로

[단계별 실행 가이드](../workflow/README.md)는 레슨을 연결하는 실무 진입점입니다. 신규 프로젝트는 Step 0부터, 기존 프로젝트는 현재 산출물을 대조한 뒤 누락된 단계부터 적용합니다.

- `docs/workflow/README.md`: 단계별 입력·작업·산출물·완료 조건·두 도구의 실행 방법을 제공합니다.
- `docs/workflow/taskflow-example.md`: 요구사항부터 검증 시나리오까지 한 기능을 연결한 작성 예제를 제공합니다. 서비스 구현이나 실행 완료 증거로 취급하지 않습니다.
- `templates/README.md`: 대상 저장소에 복사할 파일과 경로, 작성 시점을 안내합니다.
- `templates/development-workflow.md`: 대상 저장소에서 두 도구가 함께 따르는 작업 절차를 제공합니다.
- `docs/reference/official-development-guides.md`: 공식 권고와 이 저장소가 정한 운영 규칙을 구분합니다.

프로젝트 공통 산출물 경로는 PRD `docs/prd/`, 설계 `docs/architecture/`, ADR `docs/adr/`, 계약 `packages/contracts/`, Task `docs/backlog/tasks/`, 계획 `docs/plans/`, 검증 `docs/verification/`, 인수인계 `docs/handoffs/`로 합니다. 기존 레슨의 `docs/tasks/` 등 대체 경로는 기존 프로젝트에서 유지할 수 있습니다. 한 프로젝트 안에서는 단일 경로를 선택하고 참조를 일치시킵니다.

작은 수정은 기존 Task와 검증 기록에 필요한 내용을 합칩니다. PRD나 ADR을 매번 새로 작성하지 않습니다. 문서 개수와 코드 라인 수는 학습용 규모 지표이며, 실제 개발의 완료 조건은 수용 기준 충족과 검증 증거입니다.

## 4. 모듈 상세 설계

각 모듈은 3~5개의 레슨으로 구성됩니다. 레슨 형식은 [lesson-template.md](./lesson-template.md)를 따릅니다.

### Module 00 — Foundations (기초)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 00-1 | 코딩 에이전트는 어떻게 동작합니까 (에이전트 루프, 도구 호출, 컨텍스트 윈도우) | 같은 작업을 채팅 vs 에이전트로 수행하고 차이 기록 | 에이전트 세션 로그를 읽고 도구 호출 흐름도 그리기 |
| 00-2 | Claude Code vs Codex: 특성과 역할 분담 | 동일 버그 수정을 두 도구로 수행 | 비교표 작성 (속도, 정확도, 비용, 개입 횟수) |
| 00-3 | 대화형 / 헤드리스 / 클라우드 실행 모드 | `claude -p`, `codex exec`로 비대화형 실행 | 스크립트 1개를 헤드리스 에이전트로 자동화 |
| 00-4 | 실패 패턴 카탈로그 (환각 API, 범위 이탈, 무한 수정 루프) | 의도적으로 실패를 유발하고 관찰 | 본인이 겪은 실패 사례 3개를 원인/대응으로 정리 |

### Module 01 — Environment Setup (환경 구성)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 01-1 | 프로젝트 메모리: `CLAUDE.md`와 `AGENTS.md` 작성법 | 빈 저장소에 두 파일 작성, 공통부/도구별 부분 분리 | 기존 프로젝트에 메모리 파일 작성 후 전/후 결과 비교 |
| 01-2 | 권한·샌드박스·승인 모드 (`.claude/settings.json`, `~/.codex/config.toml`) | 허용/차단 목록 구성 | 팀 공용 설정과 개인 설정 분리안 작성 |
| 01-3 | MCP 서버 연결 (GitHub, DB, 문서, 브라우저) | MCP 서버 2개 연결 및 사용 | 프로젝트에 필요한 MCP 목록과 보안 검토서 |
| 01-4 | 확장 기능: Skills(구 슬래시 커맨드), Subagents, Hooks | 커스텀 Skill + 포맷팅 Hook 만들기 | 반복 작업 1개를 Skill로 패키징 |
| 01-5 | 재현 가능한 개발 환경 (devcontainer, 셋업 스크립트, 클라우드 세션) | SessionStart 훅으로 의존성 자동 설치 | 신규 팀원이 10분 안에 에이전트를 돌릴 수 있는 온보딩 문서 |

### Module 02 — Spec-Driven Development (명세 주도 개발)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 02-1 | 에이전트와 함께 PRD 쓰기 (인터뷰 방식) | 에이전트가 질문하고 사람이 답하며 PRD 완성 | Project B의 PRD 작성 |
| 02-2 | 아키텍처 설계와 ADR | 대안 3개를 에이전트에게 비교시키고 ADR로 결정 기록 | 핵심 결정 ADR 3건 |
| 02-3 | 작업 분해: Epic → Story → Task (에이전트가 한 세션에 끝낼 크기) | 설계서를 Task 명세 20개로 분해 | Task 명세 템플릿에 맞춰 백로그 구성 |
| 02-4 | 인터페이스 우선 설계 (OpenAPI, 스키마, 타입 계약) | API 계약을 먼저 쓰고 스텁 생성 | 계약 테스트까지 포함한 인터페이스 정의 |
| 02-5 | 개발용 프롬프트 엔지니어링 | 모호한 요청을 실행 가능한 작업 지시로 바꾸고 두 도구에서 비교 | 요구사항·경계 사례·검증이 연결된 프롬프트와 수정 기록 |

### Module 03 — Agentic Workflow (에이전트 작업 흐름)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 03-1 | Explore → Plan → Implement → Verify 루프 | Plan 모드로 계획 승인 후 구현 | 같은 기능을 "바로 구현" vs "계획 후 구현"으로 비교 |
| 03-2 | 에이전트와 TDD | 테스트를 먼저 쓰게 하고 실패 확인 후 구현 | TDD로 기능 3개 구현, 커밋 이력으로 증명 |
| 03-3 | Git 전략: 브랜치, 커밋 단위, PR 크기 | 에이전트에게 커밋 메시지·PR 설명 규칙 부여 | PR 템플릿 + 커밋 컨벤션 정의 |
| 03-4 | 컨텍스트 관리: 세션 분할, 요약, `/clear`, 핸드오프 문서 | 긴 작업을 3세션에 나눠 핸드오프 노트로 이어가기 | 핸드오프 노트 템플릿 작성 |
| 03-5 | 디버깅 협업: 재현 → 가설 → 계측 → 수정 | 의도적으로 심은 버그 찾기 | 버그 리포트 → 수정 PR 전 과정 기록 |

### Module 04 — Quality & Verification (품질과 검증)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 04-1 | 검증 계층: 린트·타입·단위·통합·E2E | 에이전트가 스스로 돌릴 수 있는 검증 커맨드 정의 | `make verify` 한 줄로 전체 검증 구성 |
| 04-2 | 교차 리뷰: Claude 구현 ↔ Codex 리뷰 (그리고 반대) | 같은 PR을 두 도구로 리뷰하고 지적 비교 | 리뷰 체크리스트(REVIEW.md) 작성 |
| 04-3 | 보안: 비밀정보, 의존성, 프롬프트 인젝션, 권한 최소화 | 보안 리뷰 실행 및 결과 처리 | 위협 모델 1페이지 작성 |
| 04-4 | 브라우저/E2E 검증 (Playwright 등으로 에이전트가 화면 확인) | UI 변경을 스크린샷으로 자가 검증 | UI 회귀 테스트 3개 |

### Module 05 — Scaling Up (규모 확장)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 05-1 | 병렬 에이전트: git worktree, 여러 세션, 클라우드 작업 | Task 3개를 worktree 3개에서 동시 진행 | 병렬 작업 충돌 회고서 |
| 05-2 | 오케스트레이션: 서브에이전트, 오케스트레이터-워커 패턴 | 조사/구현/리뷰 서브에이전트 분리 | 팀 전용 서브에이전트 3종 정의 |
| 05-3 | 대규모 코드베이스: 모노레포, 디렉터리별 메모리 파일, 코드 탐색 전략 | 하위 패키지별 `CLAUDE.md`/`AGENTS.md` 계층 구성 | 10만 라인급 오픈소스 저장소 온보딩 문서를 에이전트로 작성 |
| 05-4 | CI/CD 통합: GitHub Actions에서 에이전트 실행, 자동 리뷰, 자동 수정 | PR 오픈 시 자동 리뷰 워크플로 구성 | 이슈 → 에이전트 → PR 자동화 파이프라인 |
| 05-5 | 대규모 변경: 코드모드, 일괄 마이그레이션, 점진적 롤아웃 | 100개 파일 일괄 변경을 배치로 수행 | 마이그레이션 계획서 + 진행 추적 시트 |

### Module 06 — Team & Operations (팀과 운영)
| # | 레슨 | 따라하기 | 숙제 |
|---|---|---|---|
| 06-1 | 비용과 성능: 모델 선택, 토큰 사용량, 캐싱 | 작업별 비용 측정 | 월간 비용 예측표 |

## 5. 프로젝트 상세 설계

### Project A — 문서화 프로젝트 (Docs-as-Code)
- **주제**: 이 가이드 자체 또는 본인 팀의 기술 문서 사이트를 에이전트로 구축·운영
- **스택(참조)**: Markdown + MkDocs Material 또는 Docusaurus, GitHub Pages, markdownlint, 링크 체커
- **학습 포인트**: 에이전트에게 글쓰기 스타일 가이드 부여, 대량 문서 일관성 유지, 코드와 문서 동기화, 번역

| 마일스톤 | 내용 | 산출물 |
|---|---|---|
| A0 | 문서 사이트 목적·독자·정보 구조(IA) 정의 | `docs/ia.md` |
| A1 | 저장소 셋업 + 문서용 `CLAUDE.md`/`AGENTS.md` (톤, 용어집, 금지 표현) | 메모리 파일, 용어집 |
| A2 | 목차 → 페이지별 명세 → 초안 대량 생성 | 20+ 페이지 초안 |
| A3 | 사람 리뷰 + 에이전트 수정 루프, 스타일 일관성 검사 | 리뷰 이력 PR |
| A4 | 자동 검증: 린트, 깨진 링크, 코드 예제 실행 검증 CI | CI 워크플로 |
| A5 | 운영: 코드 변경 시 문서 갱신 자동 제안, 다국어(ko/en) | 자동화 파이프라인 |

### Project B — 개발 프로젝트 (풀스택 서비스)
- **주제**: 팀 업무 관리 서비스 "TaskFlow" (웹 + API + 워커 + CLI)
- **스택(참조)**: TypeScript 모노레포(pnpm + Turborepo), API(Fastify 또는 NestJS), Web(Next.js), PostgreSQL, Redis 큐 워커, Playwright, GitHub Actions
  - 다른 스택(Java/Spring, Python/FastAPI, Go)으로 진행해도 되도록 마일스톤은 스택 독립적으로 기술합니다.
- **규모 목표**: 최종 3~5만 라인, 패키지 5개 이상, 테스트 커버리지 80% 이상
- **학습 포인트**: 명세 주도 개발, 병렬 에이전트, 교차 리뷰, CI 자동화를 실제 규모에서 경험

| 마일스톤 | 내용 | 주요 모듈 |
|---|---|---|
| B0 | 모노레포 스캐폴딩, 메모리 파일 계층, 검증 커맨드 | 01 |
| B1 | PRD, 아키텍처, ADR, API 계약, 백로그(Task 명세 30+) | 02 |
| B2 | 인증/사용자/프로젝트 도메인 — 단일 에이전트 TDD | 03 |
| B3 | 작업(Task) 도메인 + 웹 UI — Plan 모드, 핸드오프 | 03 |
| B4 | 교차 리뷰 도입, E2E 테스트, 보안 리뷰 | 04 |
| B5 | 알림 워커·검색·CLI를 worktree 병렬 개발 | 05 |
| B6 | CI에서 자동 리뷰/자동 수정, 이슈→PR 파이프라인 | 05 |
| B7 | 운영 지표, 비용 분석, 최종 회고 및 아키텍처 문서 갱신 | 06 |

### Project C — 레거시 마이그레이션 프로젝트
- **주제**: 실제 오픈소스(또는 제공되는 레거시 샘플)를 대상으로 대규모 변경 수행
  - 예: JavaScript → TypeScript 전환, 프레임워크 메이저 버전 업그레이드, 모놀리스 모듈 분리
- **학습 포인트**: 모르는 코드베이스 이해, 안전망(특성화 테스트) 구축, 배치 단위 대량 변경, 진행 추적

| 마일스톤 | 내용 |
|---|---|
| C1 | 코드베이스 탐색 → 아키텍처 리버스 엔지니어링 문서 작성 |
| C2 | 특성화(characterization) 테스트로 안전망 구축 |
| C3 | 마이그레이션 계획 → 배치 분할 → 병렬 에이전트 실행 |
| C4 | 회귀 검증, 성능 비교, 마이그레이션 회고 리포트 |

## 6. 숙제(Homework) 체계

### 6.1 숙제 유형
| 유형 | 설명 | 예 |
|---|---|---|
| 🔁 Reproduce | 따라하기를 본인 환경에서 재현 | 따라하기 결과 스크린샷/로그 |
| 🛠 Apply | 배운 기법을 본인 프로젝트나 Project A/B/C에 적용 | 메모리 파일 작성 PR |
| 🔬 Compare | 두 방식/두 도구를 비교 실험 | Claude vs Codex 비교표 |
| 📝 Reflect | 회고·정리 | 실패 사례 분석 |
| 🚀 Challenge | 선택 심화 과제 | 자동화 파이프라인 구축 |

### 6.2 난이도
- ★ 기본 (필수, 30분~1시간)
- ★★ 응용 (필수, 1~3시간)
- ★★★ 도전 (선택, 반나절 이상)

### 6.3 제출 방식
1. 이 저장소를 fork 하거나 본인 실습 저장소를 만듭니다.
2. 숙제마다 브랜치 `hw/<모듈번호>-<레슨번호>` 를 만듭니다.
3. 결과물 + `submissions/<모듈>-<레슨>.md` (템플릿: [homework-template.md](./homework-template.md))를 커밋합니다.
4. PR을 열고, **에이전트 리뷰(Claude 또는 Codex) + 자기 평가 체크리스트**를 PR 본문에 첨부합니다.
5. 스터디 운영 시 동료 1명이 리뷰 후 머지합니다.

### 6.4 평가 루브릭 (공통)
| 항목 | 0 | 1 | 2 |
|---|---|---|---|
| 완료 조건 충족 | 미충족 | 일부 | 전부 |
| 검증 증거 (테스트/로그/스크린샷) | 없음 | 일부 | 충분 |
| 프롬프트/세션 기록 | 없음 | 요약만 | 핵심 프롬프트와 개입 지점 기록 |
| 회고 (잘된 점/문제/다음 시도) | 없음 | 형식적 | 구체적 개선안 포함 |

## 9. 유지보수 원칙
- 도구 기능은 빠르게 바뀝니다. 도구 특화 내용은 각 레슨의 `레시피` 섹션에 격리하고 **검증 날짜**를 표기합니다.
- 각 레슨 상단에 `last-verified: YYYY-MM-DD`, `tools: claude-code x.y / codex x.y` 메타데이터를 둡니다.
- 분기마다 에이전트로 "변경된 기능 점검" 작업을 수행하고 결과를 PR로 반영합니다.

### 9.1 학습용 설명 그림

각 모듈의 `images/`에 제안서에도 사용할 수 있는 PNG 설명 그림을 보관합니다. [DataDynamics 이미지 스타일](./architecture-image-style.md)을 적용하고, [그림 목록](./illustrations.md)과 [생성 프롬프트](./illustration-prompts.json)를 함께 관리합니다.

- 그림은 개념의 첫 이해를 돕고, 레슨의 텍스트·Mermaid·실행 레시피가 세부 조건을 설명합니다.
- 문서·폴더·모니터·체크리스트처럼 역할을 알아보기 쉬운 사물을 사용합니다.
- 이미지마다 대체 텍스트와 읽는 순서를 제공하여 그림 없이도 흐름을 이해할 수 있게 합니다.
- 도구 기능이 바뀌면 그림의 라벨·방향·설명도 함께 검토합니다. 이미지 생성일과 CLI 기능 검증일은 구분합니다.
