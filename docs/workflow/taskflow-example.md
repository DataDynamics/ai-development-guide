# TaskFlow 기능 하나로 따라가는 산출물 예제

이 예제는 [실행 가이드](./README.md)의 Step 2~9를 “프로젝트 작업 목록의 상태 필터”로 연결합니다. **아래 문서는 작성 예제이며, 구현 완료나 테스트 통과 기록이 아닙니다.** 이 저장소에는 TaskFlow 애플리케이션이 포함되지 않습니다.

## 1. 시작 상태를 확인합니다

기존 API에 로그인·프로젝트 멤버십·작업 목록 조회·테스트 DB가 있다고 가정합니다. 실제 프로젝트에서 없으면 먼저 그 기능과 테스트 환경을 별도 Task로 만듭니다. 아래 경로·ID는 이 예제 안의 값입니다. 기존 레슨의 Task ID를 가져와 덮어쓰지 않고 대상 백로그의 다음 번호로 바꿉니다.

```text
apps/api/src/routes/tasks.ts       # 기존 목록 엔드포인트
apps/api/src/services/tasks.ts     # 기존 목록 조회 로직
apps/api/tests/tasks.test.ts       # 기존 통합 테스트
packages/contracts/openapi.yaml   # 계약 원본
docs/verification/strategy.md      # 실제 검증 명령
```

경로가 다르면 실제 경로를 찾아 대응표를 작성합니다. 기존 pagination·인증 방식·오류 형식은 조사 후 유지합니다. 이 예제에서 제시하는 값과 기존 계약이 다르면 PRD와 계약을 먼저 맞춥니다.

## 2. PRD를 채웁니다

대상 파일: `docs/prd/taskflow.md`.

```markdown
# PRD: 작업 상태 필터

- 상태: 확정 (예제에서 가정한 상태)
- 문제: 프로젝트 멤버가 전체 작업 중 미완료 작업을 찾기 어렵습니다.
- 목표: API에서 상태 하나로 목록을 제한합니다.
- 비목표: 웹 필터 UI, 복수 상태, 검색, 정렬, 상태 변경.
- FR-001: 멤버는 자신의 프로젝트 작업을 status로 필터링합니다.
- FR-002: 기존 인증·멤버십 검사를 유지합니다.

| ID | 조건과 입력 | 기대 결과 |
|---|---|---|
| AC-001 | P1 멤버가 status=todo로 조회 | P1의 todo 작업만 반환합니다 |
| AC-002 | status를 생략해 조회 | 기존 기본 목록과 pagination 동작을 유지합니다 |
| AC-003 | status=unknown 또는 빈 문자열 | 400, 오류 코드 INVALID_FILTER를 반환합니다 |
| AC-004 | 비로그인 / 로그인한 비멤버 | 각각 401 / 403을 반환합니다 |
| AC-005 | 다른 프로젝트에 같은 상태 작업이 존재 | 그 작업은 반환하지 않습니다 |
| AC-006 | 일치하는 상태의 작업이 없음 | 200, items가 빈 배열입니다 |

미결 사항: 없음. status는 todo/doing/done이며 기존 도메인 값과 같다고 가정합니다.
```

사람이 확인할 질문은 “필터 조건 없이 조회하면 기존 결과를 유지합니까”, “권한 없는 사용자가 프로젝트 존재를 알아도 됩니까” 등입니다. 기존 서비스가 존재를 숨기기 위해 404를 쓰면 이 예제의 403을 그대로 적용하지 않습니다.

## 3. 설계와 계약을 연결합니다

`docs/architecture/overview.md`에 다음 흐름을 적습니다.

```text
GET /projects/{projectId}/tasks
 → 기존 인증·멤버십 검사
 → status 입력 검사
 → projectId와 status를 함께 사용한 조회
 → 기존 목록 응답 형식
```

새 패키지나 DB 스키마 변경은 필요 없다고 가정합니다. 단순 필터 추가에 별도 ADR을 강제하지 않습니다. 저장 방식이나 공개 계약의 호환성 정책을 바꾸는 경우에는 대안과 근거를 ADR로 남깁니다.

다음은 기존 `packages/contracts/openapi.yaml`의 해당 operation에 합칠 **파라미터 예제 조각**입니다. 독립적인 OpenAPI 문서가 아닙니다.

```yaml
parameters:
  - name: status
    in: query
    required: false
    schema:
      type: string
      enum: [todo, doing, done]
```

기존 path 파라미터·pagination 파라미터를 유지하고, 400 `INVALID_FILTER` 응답과 정상 예제도 계약에 추가합니다. 스키마의 enum 선언만으로 서버 입력 검증이 구현됐다고 보지 않습니다. 계약 검사와 API 통합 테스트로 동작을 확인합니다.

## 4. Task와 실행 계획을 작성합니다

대상 파일: `docs/backlog/tasks/TASK-001-status-filter.md`.

```markdown
# TASK-001: 작업 목록 상태 필터

- 상태: 초안
- 관련 요구사항: FR-001, FR-002
- 수용 기준: AC-001~AC-006
- 의존 작업: 인증·멤버십·기본 목록·테스트 환경 (실제 완료 증거 확인 필요)
- 예상 변경 범위: apps/api의 기존 목록 라우트·서비스·테스트,
  packages/contracts/openapi.yaml, 이 Task의 계획·검증 기록
- 범위 밖: apps/web, DB 스키마, 검색, 정렬

## 목표
기존 목록의 권한·pagination을 유지하면서 status 하나로 결과를 제한합니다.

## 완료 조건
- AC-001~AC-006을 통합 테스트와 기존 회귀 검사로 확인합니다.
- 검증 전략의 실제 범위 검사·필수 검사를 실행합니다.
- 계약과 동작이 일치하고 막는 리뷰 지적이 없습니다.

## 실행 전 확인
- 기존 경로와 의존 기능을 조사합니다.
- 검증 전략의 명령을 실제 실행해 확인합니다. 확인 전에는 준비 상태로 바꾸지 않습니다.
```

`docs/plans/TASK-001.md`에는 다음 순서를 적습니다.

1. 기존 목록 테스트를 실행해 기준선을 기록합니다.
2. 상태가 섞인 두 프로젝트의 fixture로 AC-001~AC-006 테스트를 작성합니다.
3. 필터 관련 테스트가 기능 미구현 때문에 실패하는지 확인합니다. DB 연결 실패는 별도로 해결합니다.
4. 계약과 입력 검증을 갱신하고 기존 조회 조건에 status를 추가합니다.
5. 범위 테스트·기존 목록 회귀·계약 검사·프로젝트 필수 검사를 실행합니다.
6. diff를 리뷰하고 실제 결과를 기록합니다.

예상 위험은 필터를 추가하며 기존 `projectId` 조건을 빠뜨리는 것입니다. 기존 권한 조건과 프로젝트 제한을 유지하는지 별도 검사합니다. 검증 명령은 `strategy.md`에서 가져오며, 특정 테스트 러너의 옵션을 추측하지 않습니다.

## 5. 같은 입력을 두 도구에 전달합니다

**Claude Code 레시피**: `CLAUDE.md`에서 가져온 공통 규칙을 확인한 뒤 아래 프롬프트를 사용합니다.

**Codex 레시피**: `AGENTS.md`와 대상 경로의 지침을 확인한 뒤 같은 프롬프트를 사용합니다.

```text
docs/development-workflow.md와 docs/backlog/tasks/TASK-001-status-filter.md,
docs/plans/TASK-001.md, docs/verification/strategy.md를 읽습니다.
선행 조건이 충족되었으면 계획 범위에서 구현·검증합니다.
API와 계약 및 필요한 테스트·작업 문서만 변경합니다.
기존 projectId·권한·pagination 조건을 유지합니다.
docs/verification/TASK-001.md에 실제 실행 증거를 남깁니다.
검증 환경이 없거나 명세와 실제 코드가 다르면 그 차이를 먼저 기록합니다.
```

한 도구로 구현하고 다른 도구로 리뷰하거나, 순서를 바꿔 사용합니다. 같은 작업 디렉터리에서 두 도구가 동시에 구현하도록 실행하지 않습니다.

## 6. 결과를 판정합니다

테스트 데이터는 테스트마다 초기화합니다. 예를 들어 P1에는 todo 작업 A와 done 작업 B, P2에는 todo 작업 C를 만듭니다. pagination 영향이 없도록 충분히 작은 fixture를 사용합니다.

| 확인 | 기대 결과 | 실제 결과 |
|---|---|---|
| P1 멤버가 P1의 todo 조회 | A만 반환합니다 | 미실행 |
| P1에서 필터 생략 | 기존 정렬·pagination 아래 A와 B를 반환합니다 | 미실행 |
| unknown 또는 빈 문자열 | 400 INVALID_FILTER | 미실행 |
| 비로그인 / 비멤버 | 401 / 403 | 미실행 |
| 프로젝트 격리 | 어떤 P1 응답에도 C가 섞이지 않습니다 | 미실행 |
| P1의 doing 조회 | 200, items: [] | 미실행 |

이 표의 기대 결과를 실제 결과 칸에 복사하지 않습니다. 실행 명령·시각·검사 대상 revision·로그를 [검증 기록 템플릿](../../templates/verification-report.md)에 남긴 후 실제 결과를 갱신합니다.

리뷰에서는 테스트가 A만 검사하고 C의 누출은 놓치지 않는지, 필터 생략 시 기존 응답이 바뀌지 않는지 확인합니다. 수정 후 영향을 받는 검사를 재실행합니다.

## 7. PR과 인계로 닫습니다

PR 본문에는 사용자의 불편, 필터의 동작, 유지한 계약, 실제 검증, 미해결 사항을 적습니다. 테스트를 실행할 수 없었다면 Task는 완료가 아닙니다. 다음 세션에 테스트 환경과 실패 재현 정보를 넘깁니다.

핸드오프에 현재 Task·계획·검증 경로, 브랜치·revision·미커밋 변경, 다음 행동을 기록합니다. API Task를 마친 뒤 웹 필터 UI를 별도 Task로 만들고 API와 연결한 사용자 흐름을 검증합니다. 웹 UI를 만들지 않은 상태를 전체 기능의 UI 완료로 보고하지 않습니다.
